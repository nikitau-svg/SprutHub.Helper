# Матрица dead-case тестов

Документ отделяет воспроизводимые проверки протокола от действий, которые временно меняют состояние пользовательского телефона. Стенд не знает настоящих адресов, серийных номеров, паролей или ID устройств и никогда не отправляет команды реальному SprutHub.

## Автоматический стенд

Локальный тестовый WebSocket изображает минимальный JSON-RPC SprutHub. Для каждого запуска создаются только фиктивные учётные данные и каталог. Проверки выполняются вместе с обычными unit-тестами:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Неподдерживаемый `server.version` | Переход на `hub.list` в том же авторизованном WebSocket |
| Неподдерживаемый `scenario.list` | Управляемые аксессуары остаются доступны, повторной авторизации нет |
| Обрыв или тайм-аут `scenario.list` | Неполный снимок отклоняется целиком, соединение восстанавливается только один раз |
| Задержанный ответ | Ответ принимается на исходном соединении в пределах тайм-аута |
| Полное отсутствие ответа | Один reconnect; после второго тайм-аута соединение закрыто и имеет статус ошибки |
| Сервер закрывает WebSocket | Активный запрос завершается сразу, клиент открывает и авторизует новый сокет |
| Внешняя отмена Android | Запрос отменяется без скрытого reconnect и без ложного статуса ошибки |
| Local недоступен или отклонил вход, cloud доступен | Режим `Авто` переходит на cloud и помечает реальный канал подключения |
| Активный local WebSocket оборван, cloud доступен | Следующий RPC восстанавливается через cloud и возвращает подтверждённый ответ |
| Оба адреса отклонили вход | Транспорт переходит в `ERROR`, оба пароля отсутствуют в исключении и диагностике |
| Ошибка до первой загрузки каталога | Интерфейсы показывают «Нет связи», а не нейтральное «Нет данных» или ложное «Онлайн» |
| Частичный каталог | Валидные аксессуары сохраняются, сломанные элементы пропускаются |
| Неизвестная обёртка ответа | Вложенный массив аксессуаров разбирается без привязки к одному внешнему ключу |
| Входящее событие характеристики | Событие доходит до подписчика и разбирается в точный `aId/sId/cId` |

## Уже проверено на Samsung Fold

- Подписанный `0.6.0-beta.4` установлен поверх `0.6.0-beta.3` без удаления приложения.
- Сохранились каталог и настройки приложения, дата первой установки, существующий виджет рабочего стола и назначенная плитка быстрых настроек.
- После обычной полной остановки процесса без `Force stop` раскрытие шторки само запустило Helper, загрузило подтверждённый кэш, заново авторизовалось локально и перечитало комнаты, аксессуары и сценарии.
- После проверки постоянный монитор телефона был снова запущен и подтверждён как foreground service.
- Подписанная `0.6.0-beta.7` установлена поверх `0.6.0-beta.5`; сохранились пароли, разрешения Health Connect и геолокации, назначение плитки и тот же экземпляр виджета One UI.
- Главный экран `beta.7` показал общую готовность; крупная панель разделила текущую и заданную температу, а «Готово» закрыло окно на рабочий стол.
- Ручное обновление виджета заново авторизовалось в локальном SprutHub, перечитало каталог и обновило тот же системный виджет без падения.
- Подписанная `0.6.0-beta.8` остановила шторм незначимых `onCapabilitiesChanged`: за несколько минут и после обычного сетевого трафика полная синхронизация запускалась только по реальным событиям, а лишний callback получил `unchanged-network-state`.
- Раскрытие реальной шторки привязало `Tile1Service`, перечитало каталог из 256 элементов и показало `Midea AC · Кондиционер` с корректным выключенным состоянием; SprutHub Helper также остался выбранным поставщиком Device Controls.
- В том же прогоне найден отдельный шторм Samsung `ACTION_BATTERY_CHANGED` при колебании тока/напряжения на зарядке; дедупликация добавлена в `0.6.0-beta.9`.
- Подписанная `0.6.0-beta.9` установлена поверх `beta.8` без очистки. Сохранились тот же виджет One UI `appWidgetId=22`, плитка №1, выбранный поставщик Device Controls, системные разрешения, foreground-монитор и четыре задачи WorkManager.
- После обновления локальная авторизация, каталог и публикация всех 12 полей телефона прошли успешно. За первые 15 минут журнал содержал только обязательный запуск монитора, реальные `screen-on/off`, три ожидаемых 5-минутных foreground-опроса и одну успешно завершённую страховочную задачу WorkManager; одинаковые callback сети и батареи не создали ни полного sync, ни даже записей событийной очереди.
- Раскрытие шторки на `beta.9` снова привязало `Tile1Service` и показало корректное выключенное состояние кондиционера. Падений, ANR и ошибок разрешений не обнаружено.
- На внешнем экране Fold сохранённый виджет 4×1 показал `Midea AC · Кондиционер · Зал · Выключено`; его отдельная кнопка обновления перечитала каталог из 256 элементов, не отправляя управляющую команду.
- Крупная панель показала локальное онлайн-соединение, раздельные текущие 26 °C и заданные 24 °C для кондиционера и второй компактный элемент. Кнопка «Готово» завершила preview-activity и вернула launcher, не открывая главный экран Helper.
- При отключении Wi‑Fi крупная панель автоматически авторизовалась через `beta.spruthub.com`, перечитала 256 элементов и честно показала `Онлайн · через облако`. После возврата Wi‑Fi ручная проверка без управляющей команды вернула `Онлайн · локально`.
- Подписанная `0.7.0-beta.7` установлена поверх `0.7.0-beta.6` при заблокированном экране. Без ручного запуска приложения шторка восстановила каталог; read-only плитка показала `Отличное` первым, а виджет, три плитки, разрешения и четыре WorkManager-задачи сохранились.
- В принудительном deep Doze с включённым системным исключением батареи успешно отработали и 5-минутный foreground-опрос, и настоящая 15-минутная задача WorkManager. Оба пути опубликовали и подтвердили все 12 выбранных полей телефона; после проверки Doze явно снят, Wi‑Fi и процесс приложения восстановлены.
- После системного `Force stop` раскрытие шторки One UI само связалось с сохранённым `Tile1Service` и сняло флаг остановленного пакета. Helper загрузил кэш из 256 элементов, вошёл локально, восстановил foreground-монитор и четыре фоновые задачи, затем подтвердил все 12 полей телефона. Это поведение Samsung проверено аппаратно, но не обещается для всех оболочек Android.
- После полной перезагрузки до первого unlock зашифрованное пользовательское хранилище закономерно оставалось закрытым. Сразу после unlock `BOOT_COMPLETED` восстановил foreground-монитор, локальный вход, каталог из 256 элементов и четыре задачи WorkManager; здоровье подтвердило доступное поле, телефон — все 12 выбранных полей.
- Одна включённая геозона снова показывалась как зарегистрированная Android и готовая в SprutHub. Тот же системный виджет `appWidgetId=22` сохранился и показал актуальное состояние, а раскрытие шторки заново привязало `Tile1Service` и поставщика Device Controls.
- В отдельном чистом прогоне на домашнем экране были отключены обе сети. Виджет сам перешёл в `Нет связи`, но после возврата Wi‑Fi и мобильной сети оставался там больше 45 секунд; только первое раскрытие шторки восстановило общий каталог и сразу обновило виджет. Так обнаружено, что успешный отдельный sync телефона не восстанавливал транспорт Android-интерфейсов.
- Для следующего подписанного кандидата добавлен независимый монитор возврата сети общего каталога с задержкой 2,5 секунды, одним повтором через 10 секунд и дедупликацией callback. Автотесты проверяют отсутствие фонового запроса при обычном старте, ограничение двух попыток, новую потерю сети во время восстановления и подавление лишнего чтения после успешной проверки интерфейса.
- Первый подписанный кандидат установлен поверх `beta.9` без очистки: подпись совпала, тот же виджет сохранился, процесс и каталог поднялись после обновления. При последующем обрыве экран был полностью погашен; сеть стала активной и валидированной, но Samsung не доставил возвратный callback каталогу. Поэтому этот кандидат аппаратный тест не прошёл и не выпускается.
- Следующая итерация ставит при `onLost` одну уникальную constrained-задачу WorkManager, а также принимает валидированное изменение capabilities как резерв пропущенного `onAvailable`. Задача делает одну попытку и завершается, исчерпанное поколение callback блокируется до нового обрыва.
- Подписанная `0.6.0-beta.10` установлена поверх `beta.9` без очистки. С погашенным заблокированным экраном и без открытия Helper или шторки обе сети были отключены, ожидающая задача получила неудовлетворённое сетевое ограничение, а после возврата валидной сети сама перечитала тот же каталог из 256 элементов и завершилась с `SUCCESS`. Существующий `appWidgetId=22` получил системное обновление.
- После ручного unlock тот же виджет до открытия Helper и шторки уже показывал `Midea AC · Кондиционер · Зал · Включено`. Раскрытая затем шторка сохранила активную плитку кондиционера, а Device Controls открылся как `Онлайн · локально` и показал подтверждённые состояние, текущие/заданные 24 °C и режим охлаждения. Первый install time, разрешения, Tile1, выбранный провайдер Device Controls и четыре задачи WorkManager сохранились; приложение подтвердило 12 полей телефона.
- Подписанный кандидат `0.8.0-beta.1` установлен поверх `0.7.0-beta.11` без очистки данных. Сохранились дата первой установки, системные разрешения и три системных виджета; старые назначения автоматически прочитались как однокарточные композиции.
- На One UI аппаратно проверены размеры `2×1`, `3×1`, `4×1` и `4×2`, выбор восьми объектов, режимы «Баланс» (`2×2 +4`) и «Подробно» (`4×2`), возврат от тестовой композиции к одиночному виджету и сохранение назначения после изменения размера.
- Преднамеренное `am crash` завершило старый процесс; foreground service и привязанный System UI provider создали новый менее чем за две секунды. Главный экран Helper не открывался, виджеты и их назначения сохранились.
- При сценарии `Wi‑Fi off + mobile data off → обе сети on` активной сети действительно не было. После возврата constrained-задача WorkManager примерно за 12 секунд перечитала каталог из 253 элементов, а событийный контур опубликовал и подтвердил все 12 выбранных полей телефона.
- При выключенном Wi‑Fi и доступном только 5G режим `Авто` авторизовался на облачном endpoint `beta.spruthub.com`, загрузил 253 элемента и подтвердил 12 полей телефона без запуска UI. После теста мобильная передача данных и Wi‑Fi возвращены в исходное включённое состояние.
- Кроме намеренно вызванного ADB `shell-induced crash` для проверки восстановления процесса, в журнале Android не было непреднамеренных падений или ANR.
- В кандидате `0.8.0-beta.3` автоматический тест нового процесса обнаружил гонку страховочной WorkManager-задачи: до загрузки кэша пустое состояние памяти ошибочно принималось за ненастроенное приложение. Worker теперь сначала читает сохранённый режим, адрес и идентификатор хаба; local-only, cloud-only и отсутствие конфигурации покрыты отдельной регрессией.
- Изолированный пакет `0.8.0-beta.3-screenshots` с `targetSdk 36` установлен рядом с основной версией на Fold под Android 17. Настоящие системные `RemoteViews` без сети и пользовательских данных проверены в размерах `57×102`, `127×51`, `130×102`, `276×102`, `349×102`, `349×220` и `554×51 dp`; контейнеры, краткие состояния, низкая полоса и сетка из восьми объектов не выходят за границы.
- Первый подписанный CI-артефакт `0.8.0-beta.3` установлен поверх предыдущей beta без очистки: сохранились дата первой установки, разрешения и три launcher-виджета. После смерти процесса страховочная WorkManager-задача самостоятельно подняла процесс при возврате сети, а виджеты показали живые значения без открытия Helper.
- Отдельный переход на мобильную сеть подтвердил облачную авторизацию `beta.spruthub.com` и загрузку 253 элементов на Android 17. При возврате Wi-Fi в первом кандидате обнаружен поздний обрыв уже после появления локального маршрута: Android не прислал callback, достаточный для нового восстановления, поэтому каталог мог остаться в ложном состоянии «Нет связи». Этот кандидат не публиковался; после добавления recovery-триггера по переходу живого каталога в транспортную ошибку последовательность повторена на финальном артефакте ниже.
- Финальный подписанный CI-артефакт с recovery-триггером повторил ту же последовательность без открытия Helper: cloud загрузил 253 элемента на мобильной сети, после возврата Wi-Fi local успел подключиться, поздний `Software caused connection abort` снова воспроизвёлся, а WorkManager автоматически переавторизовался локально и перечитал все 253 элемента примерно через 2,7 секунды. Последующая проверка шторки показала живые состояния без ложного «Нет связи»; обе сети явно возвращены во включённое состояние.

Тест не нажимал управляющую плитку и не менял состояние реальных устройств SprutHub.

## Аппаратный прогон, требующий отдельного окна

Следующие проверки временно затрагивают не только Helper, поэтому не запускаются скрытно во время обычной разработки:

1. ~~Отключить Wi‑Fi и проверить переход с local на cloud, затем вернуть сеть.~~ Пройдено на `beta.9`.
2. ~~Включить системный Doze, проверить живое событие и 15-минутную страховочную задачу, после чего обязательно снять принудительный Doze.~~ Пройдено на `beta.9`.
3. ~~Выполнить `Force stop` и проверить фактическое поведение плитки и WorkManager.~~ На One UI раскрытие шторки восстановило пакет, монитор и расписание без ручного открытия.
4. ~~Перезагрузить телефон и проверить восстановление foreground-монитора, WorkManager, геозон, виджета и плитки.~~ Пройдено на `beta.9` после первого unlock.
5. ~~Установить подписанный кандидат поверх предыдущей beta без очистки, повторить чистый сценарий `обе сети выключены → обе сети включены` без открытия приложения или шторки и подтвердить автономное восстановление общего каталога и системное обновление существующего виджета.~~ Пройдено на `beta.10`, включая визуальную сверку до открытия Helper/шторки.
6. ~~Сверить сохранение назначений виджета, плитки и Android Device Controls после обновления кандидата.~~ Пройдено на `beta.10`; все три интеграции сохранились и показали согласованное состояние.

Перед этим прогоном фиксируются исходные Wi‑Fi, состояние фонового монитора, ID виджета и наличие плитки. После каждого временного изменения выполняется явное восстановление и повторная самопроверка Helper.
