# Каталог SprutHub и правила карточек

SprutHub.Helper работает с внутренним JSON-RPC API SprutHub. Этот протокол не обещает обратную совместимость, поэтому приложение не привязывается к отображаемым именам и не считает каждую характеристику отдельным устройством.

## Иерархия данных

Каталог строится в три уровня:

1. Аксессуар — `aId`, имя, комната и сведения об устройстве.
2. Сервис — `sId`, тип, собственное имя, признаки `primary` и `linkedServices`.
3. Характеристика — `cId` и блок `control`: имя, тип, значение, чтение/запись, диапазон, шаг и `validValues`.

Адрес характеристики — только тройка `aId + sId + cId`. Одинаковые `cId` у двух сервисов одного аксессуара являются разными характеристиками. Комната, имя аксессуара и подписи могут меняться и не используются как постоянный адрес команды.

## Как несколько сервисов становятся карточками

- Внутри аксессуара Helper строит граф связей из `linkedServices`; односторонняя ссылка считается связью в обе стороны.
- Если в связанном компоненте один управляемый сервис, он становится корнем карточки, а связанные датчики — его показателями.
- Если управляемых сервисов несколько, ни один из них не удаляется и не склеивается с другим. Однозначно связанный датчик добавляется к своей кнопке; неоднозначная группа датчиков остаётся отдельной карточкой.
- Если связаны только датчики, они собираются вокруг сервиса с `primary=true`. При отсутствии такого признака используется стабильный порядок ID.
- ID карточки строится по корневому `aId/sId`. При изменении состава связей сохранённый элемент крупной панели переносится по ID любого сервиса, который реально вошёл в новую карточку.
- Неизвестная ссылка или неизвестный тип не являются поводом скрыть рабочую кнопку. Служебные сервисы вроде `AccessoryInformation` исключаются отдельно.

Такой контракт не позволяет потерять второй канал многоканального реле и одновременно не превращает температуру, влажность и батарею одного климатического устройства в ряд одинаковых плиток.

## Названия и значения

Helper использует собственное имя аксессуара, затем имя сервиса и имя характеристики. Строки могут приходить как обычный текст или как объект локализаций; выбирается язык Android с безопасным запасным вариантом.

Для перечислений читаются серверные `validValues` (`value`, `key`, `name`). Это позволяет показывать фактические названия нестандартных режимов вместо числа. Для общеизвестных состояний HomeKit остаются понятные русские запасные подписи.

## Поддерживаемые формы управления

- boolean — включение и выключение;
- числовой диапазон — яркость, положение, скорость, температура и похожие значения;
- совместная кнопка и диапазон — например питание плюс яркость или питание плюс заданная температура;
- одноразовая команда — сценарий или кнопочная характеристика;
- read-only значение — показатель карточки.

Записываемое перечисление с несколькими вариантами, несколько независимых диапазонов внутри одной карточки, медиавходы и камера требуют отдельных безопасных компонентов интерфейса. До их реализации Helper показывает текущее значение, но не подменяет выбор режима произвольным ползунком `0–100`.

## Проверяемые источники

- [spruthub-client](https://github.com/shady2k/spruthub-client) описывает ответы `accessory.list`, поля `control`, диапазоны и `validValues`. Репозиторий полезен как справочник, но не считается стабильной официальной спецификацией.
- [публичный справочник сценариев SprutHub](https://github.com/sklukin/spruthub/tree/main/docs/ScenarioTemplate) подтверждает модель аксессуар → сервис → характеристика, видимость сервисов и типы/диапазоны характеристик.
- Фактический ответ актуального хаба и регрессионные тесты Helper имеют приоритет, потому что внутренний API меняется между выпусками SprutHub.
