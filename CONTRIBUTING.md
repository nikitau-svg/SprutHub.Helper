# Участие в разработке

Спасибо за интерес к SprutHub.Helper. Проект использует внутренний API SprutHub, поэтому особенно ценны точные отчёты о совместимости с разными версиями хаба и Android.

## До начала работы

- Не публикуйте реальные hub ID, локальные или публичные IP, e-mail, пароли, токены, каталоги устройств, данные Health Connect, APK и signing-файлы.
- Заменяйте значения в логах на очевидные фиктивные примеры.
- Для уязвимостей следуйте [SECURITY.md](SECURITY.md), а не создавайте публичный issue с деталями.
- Отправляя изменение, вы подтверждаете право на него и соглашаетесь предоставить его на условиях [PolyForm Noncommercial License 1.0.0](LICENSE) вместе с обязательными уведомлениями из [NOTICE](NOTICE).

## Ветки

- `main` — стабильная, готовая к выпуску линия. Прямые push и force-push должны быть запрещены.
- `beta` — интеграционная линия для проверенных тестовых сборок.
- `feature/<краткое-имя>`, `fix/<краткое-имя>` и `docs/<краткое-имя>` — короткоживущие ветки от актуальной `beta`.

Обычный путь изменения: рабочая ветка → pull request в `beta` → тестирование beta APK → pull request `beta` в `main`. Срочное исправление можно сделать от `main`, но после слияния его нужно вернуть в `beta`, чтобы линии не расходились.

## Коммиты

Используйте короткий английский заголовок в стиле Conventional Commits:

```text
feat: add thermostat range control
fix: redact endpoint credentials in errors
docs: explain local health sync
ci: build beta artifact
```

Допустимые типы: `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`, `security`. Один коммит должен описывать одно логическое изменение. Не добавляйте сгенерированные APK, локальные настройки IDE и signing-файлы.

## Pull request

Перед отправкой:

1. Обновите ветку относительно актуальной `beta` без force-push общей ветки.
2. Запустите проверки:

   ```bash
   gradle --no-daemon :app:lintDebug :app:testDebugUnitTest :app:assembleDebug
   ```

3. Опишите, что изменилось, как это проверено и какие ограничения остались.
4. Обновите README или CHANGELOG, если изменилось поведение пользователя.
5. Ещё раз проверьте diff на персональные данные и секреты.

Изменение готово к слиянию после зелёного CI и ревью. Для изменения внутреннего протокола приложите обезличенный минимальный пример структуры ответа, если без него проблему невозможно воспроизвести.

## Выпуск

Версия и CHANGELOG обновляются отдельным pull request из `beta` в `main`. Тег создаётся только на проверенном коммите `main`. Полный процесс описан в [docs/RELEASE_PROCESS.md](docs/RELEASE_PROCESS.md).
